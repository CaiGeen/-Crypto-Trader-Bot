四、如实登记的边界与残余（不得宣称已验证）
-----------------------------------------------------------------------
1. S6k 的 False/None/True 是**桩注入的返回值**：证明"非 True 不得记成已告警/已落盘"
   这条判据有牙齿；**不**证明真实 Telegram / 邮件通道在该时点的实际投递结果。
   `send_tg_notification` 未配置 TG 时返回 None 这一事实来自第三轮复审与源码
   （:1102-1115 成功才 return True，超时/请求失败 return False），不是本轮实测投递。
2. save_batch_state 在**失败路径**上会自行发 🚨 告警（墓碑拒绝 / 写盘失败），
   那几行位于它自己的 _state_lock **之外**、却仍在 _write_monitor_error_if_owner 的
   _active_monitors_lock **之内** → 代次锁最长可能被一次 TG 超时（~5s）占住。
   影响仅是登记/接管**延后**（不产生 fail-open），彻底消除需改资金安全契约，
   **本轮未做，沿用第十轮登记，留待复审裁决**。
3. 第十轮 S6j / 本轮 S6j-1c 是**单进程内**的受控线程时序与文案断言：
   未做真实高并发 / 多进程压测；S6j-3 是 AST **结构**断言；
   S6j-1c 只断言文案内容，不判定人工按文案处置是否正确。
4. S6j 未覆盖"补挂出一张带数量的真止损"（沿用第九轮 S6f-4 的既有未验证项）；
   test_sg3_p1 的 11 场景仍为手工构造的 ccxt 字段夹具；
   _ccxt_order() 不是"实际脱敏载荷校准"。
5. 两个既有 rc=1（test_m2_m4_maintenance / test_recover_semantics）本轮**未修**，
   需另行排期。
6. 17 文件累计差异**未**做逐项发布级审查。
