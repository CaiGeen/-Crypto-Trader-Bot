# 项目接手与复现指南

> 面向第一次接触项目的人，以及需要快速建立完整上下文的 AI。
> 编写日期：2026-10-14。本文是**源码回顾与操作指南**，不是实盘部署指令。

## 1. 一句话说明

这是一个运行在 Binance USDⓈ-M 永续合约上的 Python 交易执行与风险管理系统：
用户通过 Telegram 提交交易计划，程序分层挂单、追踪成交、管理批次止损止盈、处理平仓与恢复，
并把已实现盈亏先暂算、再用交易所流水证据核验。

它的核心价值不是“自动发现稳赚的买卖点”，而是**把人为给出的交易计划转化为可跟踪、
可恢复、尽量避免重复操作的订单生命周期**。

你应当把它理解成三层：

1. **交易控制面**：Telegram 命令、授权用户、信号解析、去重、交互确认。
2. **交易执行面**：CCXT 与 Binance 对接、批次账本、条件单、成交确认、保护单、平仓。
3. **运行与证据面**：watchdog、健康巡检、通知预算、日志、对账和离线测试。

## 2. 适用对象与不适用对象

适合：

- 已理解合约风险，愿意自行确认交易信号与风险预算的使用者。
- 需要多层入场、批次级管理、Telegram 远程控制和故障恢复的维护者。
- 希望研究订单一致性、证据链、异常恢复及金融状态机的开发者。

不适合：

- 期待程序自动生成可靠交易策略、保证收益或保证不亏损。
- 把“测试命令”“dry-run”“小数量”理解成天然没有实盘影响。
- 在未知账户状态、缺失账本、未知订单归属时直接接管真实账户。
- 只复制源码、不核对依赖、配置、交易所模式和历史状态就启动。

## 5. 当前功能地图

### 5.1 用户能做什么

- 提交 JSON 或快捷信号：指定交易对、方向、杠杆、每层触发价/数量/止损及整体止盈。
- 查询活跃批次、交易所持仓汇总、系统状态。
- 按 batch_id 管理保本、止盈/止损、部分减仓、市价或限价平仓。
- 撤销在途限价平仓，把控制权交回批次监控。
- 在发生鉴权封锁后，走显式探活和对账恢复流程，而不是手工删除锁。

### 5.2 程序后台做什么

- 每个批次独立追踪入场订单、成交证据与保护单注册表。
- 启动时恢复历史活跃批次；没有成功恢复不会进入可正常接受新风险的 READY 状态。
- 通过 API 限流/串行化/冷却与分类恢复避免无限高速请求。
- 在看不清订单/持仓事实时倾向阻止新增风险，而不是猜测“没有订单”。
- 原子持久化账本，记录清账墓碑，处理平仓并发、幂等和崩溃续跑。
- 暂算盈亏，后台查成交和 Income History，在证据完整时升级为权威对账结果。
- watchdog 记录主程序输出与进程心跳；独立巡检读取健康状态并按事件发告警。

### 5.3 项目还有什么

- `strategies_backtest/`：回测研究脚本、独立依赖和数据输出，不是实盘默认执行链。
- `backtest_strategies/`：另一组研究/辅助文件，不要默认等同于生产策略。
- `tests_archive/` 与 `送审附件_*`：历史用例、方案与 helper；正式门禁会忽略归档测试目录，
  但部分现役脚本仍会从附件 helper 中提取函数用于测试，不能随手删除附件目录。
- 大量事故、设计、部署和审查文档：提供演进背景，不自动构成当前授权或当前行为。

## 6. 技术路线

| 层面 | 实现 |
|---|---|
| 语言 | Python，当前已验证环境为 3.11.1；源码需要至少支持 `X \| None` 的现代 Python |
| 交易所适配 | `ccxt==4.5.68`，Binance USDⓈ-M `binanceusdm` |
| Telegram | python-telegram-bot 22.8 及以上，asyncio + HTTPXRequest，getUpdates 长轮询 |
| 同步交易与异步交互衔接 | handler 使用 executor 调用同步交易方法；批次监控为线程 |
| 持久化 | JSON 文件、进程内锁、同目录临时文件 + replace；关键路径有 flush/fsync |
| 金融对账 | 标识归属、证据完整性、Decimal、资金费分配和非 USDT 费用估值 |
| 服务守护 | Windows 环境为主要验证目标；子进程 watchdog、具名互斥体、计划任务 |
| 通知 | Telegram + 事件文件队列 + 有明确事件政策的 QQ STARTTLS 邮件 |
| 验证 | pytest 可收集用例 + 单独执行的脚本式测试，仓库门禁统一管理 |

这不是数据库服务 + Web 前端的典型架构：它是一个本地文件型、线程与异步并存的交易程序。
文件路径、工作目录、恢复状态和副作用隔离，往往比“页面是否能打开”更重要。

## 7. 最重要的安全认知

1. `bot_runner` 和 `quick_trade` 构造 trader 时使用 `is_demo=False`，默认真实账户路径。
2. `/test` 会生成并执行真实挂单；“远离市价”不是不会成交的保证。
3. `reconcile_pre_launch.py` 的“只读”指没有下单/撤单，不代表零网络或不消耗 API。
4. 普通启动、恢复、巡检都可能发生 API 查询、状态写入、通知，不能当成纯导入自检。
5. `.env`、账本、通知队列、锁、日志不是可随手清空的缓存。
6. 程序的安全护栏不保证不存在滑点、强平、网络故障、外部手工订单或交易所行为差异。
7. 本套文档不授权 AI 创建/撤销真实订单、启停生产、变更代理、部署或回滚。

## 8. “复现成功”应该如何定义

分层验收，不能把其中一层冒充全部：

- **源码可读**：知道入口、模块职责、数据文件和危险命令。
- **环境可装**：干净 venv 中安装依赖，记录确切版本。
- **离线可验**：无真实凭证，现役测试完成，解释通过/跳过/警告/未验证。
- **联机可查**：经授权，确认实际账户模式、权限、读 API 与通知通道。
- **业务可跑**：经授权和风险预算，一笔有确切 batch/order/trade 归属的流程跑完。
- **盈亏可核**：成交、实际佣金、资金费、返佣、估值与分页完整性足以支持权威结果。
- **恢复可证**：在隔离环境先验证状态机；真实中断演练另需授权，不能用重启生产证明自己。

在没有账户、网络、凭证、行情数据和批准的生产状态材料时，AI 可以大概率复现**离线整套程序与测试**，
不能声称复现同一笔实盘交易或获得同样的交易收益。
