# AI 接手契约与完整验收清单

[返回总览](README.md)

## 1. 先把任务分成三种

### A. 理解/文档/代码审查

允许阅读仓库源码、测试与脱敏历史材料。
不默认允许读生产 `.env`、账户账本、调用 API、重启、改代理或恢复实盘。
不要为了了解类初始化就构造真实 trader 或运行主入口。

### B. 隔离开发与测试

在干净 worktree/VM 中修改明确范围的文件，使用假配置、fake exchange 和临时状态。
具体隔离测试可能允许写临时材料；不要把权限扩展到生产目录。
完整门禁需要正确 ignore 集合，必要时先审批运行条件。

### C. 真实运行/维护

先明确“读取”和“改变”的授权边界：

- 读本地统计 ≠ 可读凭证。
- 只读 API ≠ 可下单或撤单。
- 允许查询 ≠ 可启动 trader/恢复链。
- 停机窗口 ≠ 可部署/回滚/清账。
- 审查通过 ≠ 可合并；合并通过 ≠ 可部署。
- “快速跑通” ≠ 可以任选标的、杠杆和最大损失。

本次文档/实验工作不能当成下一次维护的永久授权。

## 2. 第一次接手的推荐探索顺序

1. **确认位置**：工作目录、Git 状态、分支、head、是否有人未提交工作、是否已有 open PR。
2. **读本套文档**：尤其业务副作用矩阵与架构不变式。
3. **找入口**：`watchdog.py`、`bot_runner.main`、`on_post_init`、启动恢复函数。
4. **找模型**：`TradeSignal`、`execute_signal`、主状态结构、注册表、close_phase。
5. **找副作用**：CCXT、socket、SMTP、Telegram、状态/日志文件、后台线程创建。
6. **找验收**：针对性测试，再看 run_test_gate 的集合/基线/拒绝条件。
7. **核对任务范围**：先提出最小方案，确认哪些操作必须等待授权。

大型 trader 文件不适合全部一口气读完后猜测。先 grep 函数名与调用方，
沿相关路径读实现、状态写入和测试；优先依据名字，不依赖旧文档行号。

## 3. 必须交给下一位 AI 的最小上下文包

```text
仓库地址、工作目录、分支、commit：
这是哪个任务（bug/审查/文档/演练），关联 PR/issue：
范围内允许修改的文件/行为：
硬边界：生产路径/凭证/API/订单/账本/通知/备份：
当前状态：生产是否运行（谁确认、何时；不能只凭旧聊天）：
明确事实与未决假设：
已完成测试（命令、commit、环境、完整计数、rc）：
证据附件路径及脱敏状态：
候选/冻结包/回滚材料是否允许读取或修改：
待做事项、最小下一步、停止条件：
```

新 AI 不应自动假定本机某个未跟踪 `.env` 可以用，也不应扫描整个用户目录寻找密钥。
从源码存在 `start_pnl_reconciliation` 推断“运行进程已启动对账”是错误推理。

## 4. 文件/代码修改的约束

- 不改变计划数量与真实成交数量的语义，不用 expected side 冒充 observed side。
- 不把异常捕获范围扩大后称为根因修复。
- 不把读取失败改成空状态从而放行下单/清账。
- 不把对账暂算 promoted 为权威值来让日报看起来完整。
- 不删除去重/硬锁/墓碑或样本污染来让门禁变绿。
- 不为运行一个测试替换真实函数的业务逻辑，除非测试明确模拟该依赖。
- 不在 fake Application 上启动无限 watcher；测试退出后线程可能污染下一组用例。
- 任何全局变量/模块/环境修改用 finally、mock context 或 fixture cleanup 恢复。
- 多线程 fake 对象的 MagicMock 不能代替“必须明确为 True”的业务布尔值。
- 修改 JSON 状态结构时说明旧记录兼容性、降级和迁移；不能默认所有历史值都是新 schema。

## 5. 完整项目复现验收清单

### 源码与环境

- [ ] 知道使用的是哪个 commit，不把 main/冻结包/生产 overlay 混为一谈。
- [ ] Python/Windows/CCXT/PTB/HTTPX 等实际版本已记录。
- [ ] 独立 venv，`pip check` 通过；不使用生产解释器安装依赖。
- [ ] CWD、`__file__` 文件定位和硬编码运维路径已核对。
- [ ] 没有复制生产 `.env`，没有真实 token 出现在输出/报告。

### 离线逻辑

- [ ] parser 教学信号能解析，错误字段能拒绝，未执行交易。
- [ ] Telegram 配置固定、main 接线、诊断保真测试通过。
- [ ] 收集测试与脚本测试均执行，不能省略其中一段。
- [ ] 所有 passed/skipped/warnings/NOT-VERIFIED/rc 原样记载。
- [ ] 测试构造前状态重定向、网络阻断/绊线已确认。
- [ ] 无测试遗留影响生产；checkout 哨兵无变仅是有限证据，不是绝对保证。

### 联机（如果明确授权）

- [ ] 正确账户/网络/白名单/权限；无提现权限；无第二交易进程。
- [ ] 持仓模式、normal/algo 未结订单与本地批次状态能够解释。
- [ ] READY 是恢复成功，不是仅初始化对象或 Telegram 开始监听。
- [ ] Telegram/SMTP 接受与最终送达边界分开，通道自检外发已获授权。
- [ ] API 查询窗口、分页/满页及请求预算有证据。

### 交易与对账（如果明确授权）

- [ ] 逐笔风险预算明确，不自行选择数量/杠杆。
- [ ] 实际成交数量、成本、方向、positionSide、order/trade ID 完整。
- [ ] SL/TP 核验事实明确，不只看本地 ID 或挂单成功文案。
- [ ] 平仓/减仓/撤销的 batch owner、实际成交与终态一致。
- [ ] 暂算 vs 权威净盈亏区分清楚；资金费/返佣/非 USDT 费用折算足够完整。
- [ ] 没有把截图舍入金额或账户余额差当成精确批次净盈亏。
- [ ] 对账不完整保持 blocker，不造零费用/零资金费补齐。

### 交付

- [ ] diff 范围窄、没有无关运行文件或个人资料。
- [ ] 文档链接能打开，示例不会隐式执行实盘命令。
- [ ] PR/issue 关联、测试环境、已知风险和未决项清晰。
- [ ] 不擅自合并/部署/重启；只有对应明确授权才进入下一步。
- [ ] 旧 R3/R2 冻结包和回滚备份未改、未移、未清理。

## 6. 常见误判与正确回答

| 误判 | 正确回答 |
|---|---|
| “新 worktree 就安全，不需要网络隔离” | 凭证/硬编码路径/导入/子进程可穿透目录隔离 |
| “小订单不需要下单授权” | 金额大小不改变权限边界 |
| “`/test` 不会成交” | 真实挂单，远价只是条件，市场可变化 |
| “空 open orders 就清账” | 需 normal/algo 双通道、成交/持仓与归属证据 |
| “WinError 5 是 ACL，改权限就好” | 读句柄/共享/占用/过滤驱动等需定点证据 |
| “130s 比 read=120s 多了 10s，说明网络层 bug” | PTB long-poll timeout 相加；响应迟到根因另查 |
| “手续费 actual，就说明全部净盈亏权威” | 还需 gross/funding/rebate 与估值/分配完整性 |
| “市场正常时测试通过，就能保证 SLA” | 轮询档位测试不包含真实网络与 API 阻塞时延 |
| “一轮测试 rc=0，所有用例都执行了” | 还要区分脚本/pytest、skip 与 warning |
| “合并 PR 后应重启生产验证” | 合并不是部署授权，文档/fixture 无需生产重启 |

## 7. 证据阅读的优先级

1. 当前任务授权与具体边界。
2. 精确 commit 的源码和对应测试。
3. 有时间、环境、命令与完整结果的验证报告。
4. 交易所实际成交/Income 身份与完整窗口证据。
5. 历史设计文档、注释、旧 README 与对话。

这不是说历史文档没价值，而是**历史意图/曾经实测**不能覆盖当前实现和新的账户事实。

## 8. 推荐首轮交接结论格式

```text
我已理解：交易执行/批次管理系统，不是自动收益保证。
当前基线：branch/commit + 关键依赖版本。
复现等级：源码/离线/联机/实盘/权威对账中的哪一层。
本轮实际做了：
本轮没有做：生产文件/凭证/API/通知/订单/重启/部署。
测试：命令 + pytest/脚本完整计数 + rc。
发现的根因证据和未决事项：
下一步：一个最小行动 + 是否需要授权 + 结束条件。
```

## 9. 若需从零重建类似程序

按能力而非按一个大文件的行号推进：

1. 建 TradeSignal 模型、纯 parser 与输入负测。
2. 建可替换 exchange adapter，先 FakeExchange，再经批准的真实读取。
3. 建批次持久状态、原子更新、墓碑和错误读取 fail-closed。
4. 建创建意图/核验身份/注册表，再实现实际 ENTRY/SL/TP。
5. 建实际成交数量/成本证据、监控生命周期和保护更新事务。
6. 建平仓 owner/freeze/finalizer、部分减仓守恒与撤销恢复。
7. 建暂算记录、dedup、纯对账规则和持久 worker。
8. 建 Telegram 授权/指纹/命令，用 executor 衔接同步交易。
9. 建限流/鉴权盲区/恢复 READY 与低风险通知政策。
10. 最后建 watchdog/独立巡检/日志/运维与完整门禁。

不过，本仓库已经有多轮事故修复和兼容状态机，重写很容易丢掉边界条件。
为复现现有程序，优先使用完整源码和现役测试，不要只依据文档重写然后宣布行为等价。
