# 业务使用与净盈亏核验

[返回总览](README.md) · [下一篇：运维与测试](04-operations.md)

> 本篇用于理解业务，命令和价格示例不授权真实执行。
> 实盘授权至少包括：账户、标的、方向、数量/名义价值、杠杆、最大损失、退出方式及允许的 API 操作。

## 1. 从用户角度理解一笔交易

你不是给程序一句“看好 BTC”，而是给它一份**执行计划**：

1. 哪个交易对，做多还是做空。
2. 希望每层在什么价格触发、成交多少基础币数量。
3. 每层止损在哪里；整体止盈在哪里。
4. 杠杆多少；是否符合账户、风险闸门和已有批次状态。
5. 程序收到信号后执行/监控，用户按 batch_id 管理后续操作。

杠杆并不会替你改变 `amount` 字段单位：BTCUSDT 的数量通常是 BTC，不是 USDT 保证金。
例如 `amount=0.001` 表示计划买/卖 0.001 BTC，而不是投入 0.001 USDT。
实际数量还需 CCXT market 精度、最小量/最小名义价值检查。

## 2. JSON 信号

```json
{
  "symbol": "BTCUSDT",
  "side": "BUY",
  "leverage": 2,
  "entries": [
    {"trigger_price": 80000, "amount": 0.001, "stop_loss": 79000},
    {"trigger_price": 80500, "amount": 0.001, "stop_loss": 79500}
  ],
  "take_profit": 82000,
  "initial_stop_loss": 79000
}
```

这是教学格式，不是基于当前市价的建议。不能因为 trigger 远离当前价格就认为安全。

| 字段 | 含义/约束 |
|---|---|
| `symbol` | 如 BTCUSDT；实际可交易品种还要经过 market 查询 |
| `side` | BUY=策略多方向，SELL=策略空方向；入口校验与下游方向核验均重要 |
| `leverage` | 正整数，至少 1，并受 `MAX_LEVERAGE` 限制 |
| `entries` | 非空数组，每层包含 trigger_price、amount、stop_loss |
| `trigger_price` | 正数，计划触发价，不代表最终成交价 |
| `amount` | 正数基础币数量；parser 有大数量防误操作校验，非充分风险控制 |
| `stop_loss` | 正数；缺省可用 initial_stop_loss，方向和单调性还要下游校验 |
| `take_profit` | 正数，整体目标止盈 |
| `initial_stop_loss` | 正数，初始止损约束 |

parser 会生成包含日期时间和随机后缀的 batch_id。
不要把另一个用户的历史 batch_id 复制到自己的状态文件，也不要假定相同 JSON 获得相同 batch_id。
信号去重另由控制面指纹/状态管理，不是仅靠 batch_id 相同。

基础解析不是全部业务校验：方向、持仓模式、实际账户余额、SL/TP 合理性、订单归属等
在后续 trader/handler 中继续检查。不要看到 parser 返回对象就宣传“该单可安全执行”。

## 3. 三种提交方式

### JSON 文本 / JSON 文件

经授权用户可在 Telegram 发送 JSON 文本或上传 `.json` 文件。
程序 dispatch 时使用信号内容快照，避免两次发送覆盖 `signal.json` 后串单。
`signal.json` 是辅助留存，不是可靠持久化执行队列。

### 快捷命令

```text
/signal Symbol Side Leverage EntryPrices Amounts StopLosses TP InitialSL
```

EntryPrices/Amounts/StopLosses 是逗号分隔数组，层数必须对应，例如：

```text
/signal BTCUSDT BUY 2 80000,80500 0.001,0.001 79000,79500 82000 79000
```

**发送上述命令给真实 bot 会执行业务，不是仅展示草稿。** 初次接手请只在离线 parser 中验证格式。

### `/test` 命令

当前参数是：

```text
/test Symbol Side Leverage
```

第三个参数是杠杆，不是数量。历史 README 中 `/test <AMOUNT>` 口径已经不准确。
该命令查询市价并构造远离市价的真实挂单，然后进入执行链。
远离市价不能保证永不成交，它**不是 mock、不是 dry-run、不是纯通知自检**。

## 4. 命令及副作用矩阵

| 命令 | 当前用法 | 主要副作用 |
|---|---|---|
| `/start`、`/help` | 无参数 | Telegram 回复；无下单意图 |
| `/status` | 无参数 | 批次查询/回复；不要泛化为完全零 API 的承诺 |
| `/summary` | 无参数 | 持仓/浮盈汇总，可查询交易所 |
| `/system` | 无参数 | 运行信息/回复 |
| `/signal` | 八类参数，或发送 JSON | 创建批次、持久化、真实下单 |
| `/test` | Symbol Side Leverage | 真实查询与挂单 |
| `/be` | batch_id | 修改保护策略，可能创建/撤销保护单；并非保证净盈亏为零 |
| `/tp` | batch_id price | 修改止盈；帮助中可能隐藏但仍注册 |
| `/sl` | batch_id price | 修改止损；涉及订单与状态事务 |
| `/close` | batch_id | 交互式选择平仓路径与执行 |
| `/partial` | batch_id amount | 指定批次部分平仓及保护数量重建 |
| `/closecancel` | batch_id | 撤销在途限价平仓；根据部分/完全成交事实结算或恢复保护 |
| `/cancel` | batch_id | 管理未成交入场单，不等于强行平掉整个账户 |
| `/force` | 指纹短码 | 一次性重复信号放行，随后需重发；不是直接下单，但仍是危险批准 |
| `/auth_reset` | 无参数 | 真实鉴权探活→恢复对账→解锁；不得当无副作用查询 |

所有命令先检查授权用户。一个未授权用户看到 bot 在线，不代表可以执行操作。
批次卡片和按钮最终仍进入相应业务方法；不要把按钮视为另一条可绕过安全门的入口。

## 5. 最小业务路线与验收

### 路线 A：已有成交的只读核验（最快、无新增资金风险）

1. 用户指定一笔已有平仓交易或从经授权的统计文件选取候选。
2. 排除 `batch_A` 等测试夹具样本；不能只按“最后一行”认为是真实记录。
3. 对齐 symbol、方向、数量、开/平时间和 order/trade 身份。
4. 读取本地暂算值及费用来源标记；计算本地公式是否自洽。
5. 用户提供脱敏成交、Income/资金费、佣金资产及折算证据。
6. 出具“显示一致”“暂算一致”“权威精确核验”中的实际等级，列出差异。

这条路线不要求重启、下新单或运行后台 worker。

### 路线 B：新的一笔受控实盘流程（另外授权）

1. 确认程序版本、已恢复 READY、账户模式、已有持仓/订单及风险预算。
2. 确认标的最小交易量、名义价值、杠杆、保证金和可接受最大损失。
3. 只发一份信号，保留 batch_id、入场 order ID 和成交 trade ID。
4. 成交后核验方向、实际数量、实际均价及 SL/TP 身份；不要仅看“挂单成功”。
5. 通过指定批次的正规平仓路径退出，核验未结订单、实际成交与账本终态。
6. 查看暂算记录、后台对账状态与交易所证据。
7. 报告完整流程及未核验事项；权威对账延迟不应迫使重复交易。

不要用 `/test` 代替这一套风险授权；不要为了最快把杠杆设成 100。

## 6. 手工操作为什么有风险

同一个 symbol/方向可能有多个本地批次，但交易所账户只有汇总持仓。
在 App 上手动平掉一部分汇总仓位，程序未必能唯一判定应减哪个 batch。
明确归属的部分平仓应该用 `/partial batch_id amount`。

程序会监测外部变化，并可能阻断新风险、保留未知减仓标记或处理保护恢复；
不能保证“随意手动撤掉 SL 再等程序补回来”在任何网络状态都安全。
事故演练里曾验证过某些自愈路径，不是对未来任意撤单实验的授权。

## 7. 净盈亏：两套数与一条证据升级链

### 7.1 下单时没有已实现盈亏

下单阶段算数量、保证金和风险预算。
开仓成交后得到实际成本与佣金；只有减仓/平仓后，才有对应已实现盈亏。

### 7.2 本地暂算

对线性 USDT 合约，最基本的计算是：

```text
多头毛盈亏 = (实际平仓价 - 实际开仓成本) × 实际平仓数量
空头毛盈亏 = (实际开仓成本 - 实际平仓价) × 实际平仓数量
暂算净盈亏 = 毛盈亏 - 本条分摊入场费 - 平仓费
```

实际程序还需要处理多层加权成本、部分减仓、先前减仓未知以及费用不可用。
订单的计划触发价不能冒充实际均价；缺平仓价不能回退成本价并虚构毛盈亏为零。

`_record_realized_pnl` 会保留 `local_provisional_net_pnl`、费用来源、`pnl_source`、
`accounting_status`、`pnl_not_authoritative` 等。已有旧记录可能没有这些新字段。

### 7.3 权威对账

后台 worker 在恢复成功后启动，每个循环约 15s 检查任务，不代表每 15s 无条件查询所有接口。
单轮任务有请求预算（最多六次物理请求、权重 90），按持久化游标与计划推进。

主要流水类型：`REALIZED_PNL`、`COMMISSION`、`FUNDING_FEE`、`COMMISSION_REBATE`。
最终按带正负号的现金流求和：

```text
权威净盈亏 = realized + funding + commission + rebate
```

commission 通常为负值；若用“费用绝对值”的口径表达，才是减手续费。
不要对已经为负的佣金再次减去，造成符号错误。

完整证据至少包括：

- 入场与平仓 trade/order identity、时间、方向及 positionSide 可归属。
- 成交查询与 Income 查询窗口足够完整；满页不能自动视为没有遗漏。
- 手续费记录能与成交匹配，未重复扣除。
- 非 USDT 资产（例如 BNB）按实现要求的事件分钟 mark 数据估值，不能用当前币价替代。
- 资金费需有持仓时点与方向/批次归属，不能把账户净资金费直接塞给某批次。
- 手工/外部减仓、对冲方向、返佣或缺证据都有相应明确处理，不能靠余额差猜测。

对账函数只有完整性、估值和分配都成立才返回可升级的权威金额。

### 7.4 延迟与 finality

当前源码安排平仓后 0、60、300、900、3600、21600、86400 秒，以及 72 小时、7 天等
时点的扫描计划；`finality_at_ms` 为平仓后 72 小时，自动扫描窗口至 7 天。
因此“平仓后马上没有 AUTHORITATIVE_FINAL”未必是程序故障。

Income 可能迟到，历史记录可能缺 trade evidence，存在 blocker 的任务不会因时间到了
就自动被当作准确。超过窗口仍缺证据可能 STOPPED/UNKNOWN，需要人工核验，不能无限扫描。

### 7.5 为什么截图只支持有限结论

例如某笔 BUY 0.002 BTC：

- 本地均价 85,525.0，截图均价 85,525.1；平仓价都是 85,528.7。
- 0.1 的均价差对 0.002 BTC 是 0.0002 USDT 毛盈亏差。
- 本地净盈亏 −0.1123，截图显示 −0.11，显示舍入后吻合。
- 截图佣金 BNB 只显示四位小数，本地费用来源为 estimated。

这不能证明精确金额对齐。应补未舍入的成交佣金、资产估值与资金费证据；
资金费页面显示 0.00 也存在显示精度和页面覆盖边界。

## 8. 日报和浮盈不是同一个口径

- `/summary` 主要涉及当前账户/持仓快照与浮动盈亏，随行情变化。
- 已实现记录来自实际减仓/平仓，可能有本地暂算与权威版本。
- 日报默认北京时间早间窗口，发送状态和重试有持久化机制。
- 收益记录去重避免双线程重复落账，但历史测试样本污染仍需人工识别。
- 账户总余额变化还可能包含充提、跨资产转账、资金费、其他交易，不是某批次净盈亏。
