## 1. 如何读这份清单

- **已确认实现/接口问题**：可以从当前源码或已有证据直接确认，不等于已发生资金事故。

- **可用性/维护取舍**：目前保守做法合理，但未来负载或操作成本可能要求改善。
- **待归因事件**：症状已见，不能据此宣称生产根因已确认或需要立刻改代码。

优先级表示建议的决策顺序，不是发布承诺。未验证的假设不写成确定缺陷。

## 3. 日亏损风控不能直接等同于最终财务核算

### 已确认的源码条件

- `_check_account_risk` 仅在 `RISK_DAILY_REALIZED_LOSS_LIMIT > 0` 时查询当日盈亏。
- `_get_today_realized_pnl` 将当日非 `AUTHORITATIVE_FINAL`、非完整权威来源的记录判为未对账。
- 未对账时，该日亏损闸门 fail-closed 拒绝新批次。
- 当前对账任务有平仓后 72h 的 finality 条件，不能在当天直接获得同一笔新平仓的最终权威状态。

因此，在启用该闸门且当天产生暂算平仓记录后，新批次可能因“证据尚未最终确认”而被拒绝，
即使尚未达到亏损上限。这是实时风控与最终财务口径的时间不匹配。

### 当前状态的边界

用户确认目前没有设定亏损上限；若有效值为 `0`，源码不会进入上述检查，
所以**当前不会被此项时间冲突阻断**。这是基于配置条件的判断，本轮没有读取生产 `.env`。
与此同时，`0` 意味着没有启用这道当日亏损上限保护，不代表它提供了零亏损保证。

### 准备启用之前应做

分别定义即时风险口径与最终财务口径，明确未决证据、保守费用、收益与亏损如何处理，
用相关风险/对账测试证明安全边界。不能把估算升格为权威，也不能通过删除统计解除闸门。

## 4. 批次是本地归属模型，不是交易所独立账户

交易所按 symbol/positionSide 汇总仓位，本地按 batch_id 分配成交和风险。
同方向多个批次与 App 汇总减仓结合时，归属会更复杂。

**当前支持不同方向批次并存**：同一 symbol 在 Hedge Mode 下可以同时管理 LONG/SHORT。
One-way 模式下买卖作用于净仓位，不能理解为两个独立方向仓位。
`execute_signal` 会查询 `dualSidePosition`，查不清即拒绝开仓。
并存仍受 READY、批次上限、资金、保护状态和创建未决等门约束。

“优先减少同方向多批次复杂度”是操作建议，不是说代码不支持多空并存，
也不是本轮对当前账户模式的联机确认。

改进方向：区分显示交易所总仓位与本地批次分配，管理同交易对共享杠杆/账户参数；
部分减仓优先通过 `/partial batch_id amount` 明确归属。出现实际归属冲突再设计最小修复。

## 5. `/test` 不是离线演示

当前 `/test Symbol Side Leverage` 会查真实市价并构造实际执行信号；第三参数为杠杆。
远离市价只是一种挂单条件，不能保证永不成交。名字和历史 README 的参数口径易误导初次使用者。

本指南已明确危险性。后续可考虑把无网络的“预览计划”和经过确认的“实盘演练”分成不同入口；
在未经行为变更审查前，不能偷偷把现有命令改成模拟，或因为名字叫 test 就运行它。

## 6. 阻断要保守，但处置应当更明确

创建未决、保护单硬锁、鉴权封锁、未知减仓、成本待补证和财务对账 blocker 属于不同原因。
目前分散在多个状态结构和提示中，使用者可能难判断哪些查询/退出操作仍可执行。

建议的产品改进是统一的只读阻断解释：原因、缺什么证据、受影响范围、可执行操作、
恢复前提和人工接管步骤。它不能变成一键清锁/一键清账，也不应绕过恢复事务。

## 7. JSON 持久化和大交易类的维护成本

多文件保存批次、墓碑、统计/对账任务、鉴权和通知预算；它们不能凭一次 rename 自动成为跨文件事务。
大交易类、线程与 asyncio 共存也提高了验证范围和测试夹具装配成本。

这是维护与一致性边界问题，不是已经证明账本正在丢数据。
近期应优先明确数据所有权、持久化顺序、旧记录兼容、恢复与证据留存。
若真实维护成本或一致性故障达到阈值，再评估事务存储与模块拆分。
数据库迁移不能解决交易所外部副作用、未决创建与批次归属，也不能未经批准迁移生产状态。

## 8. API 方案：有防风暴措施，不是永不限流的保证

### 已有保护

`_safe_api_call` 和相关代码包含：

- trader 实例共享信号量、最小调用间隔与 CCXT rate limit。
- 每次重试前等待共享冷却。
- 429 设置共享冷却并考虑 Retry-After；418 按封禁时间冷却。
- 明确鉴权拒绝进入 AUTH_BLOCKED，停止无意义重试。
- 有限次数网络重试，特定事实终态不再重试。
- 对账单轮请求/权重预算，API 指标快照及告警去重/通知预算。

因此，**不能把共享通道本身写成 API 熔断风暴已复发的原因**。
本轮没有新的生产证据证明当前风暴复发，不做预防性的并发、代理或重试调整。

### 仍需区分的边界

- 串行化能限制并发，但不等于完整的账户/IP 加权配额调度。
- 信号量和冷却主要属于一个 trader 实例，不统一管理其他进程、独立巡检或共享出口上的客户端。
- 同步方法背后实际请求数、外层反复轮询和高权重端点仍需真实指标解释。
- 长查询占用 API 通道可能延后保护相关操作；这与请求风暴是不同风险。

自然再现时应核对端点次数、weight/order-count、Retry-After、其他客户端和冷却期间实际调用。
若证实关键操作排队过久，再审查优先级调度；不能简单增加并发来解决等待。
源码能力和历史测试通过不能证明当前运行进程/共享出口一定处于同样受控状态。

## 9. 配置与历史文档的维护债

模板、代码默认值、Telegram 项目配置与 trader/巡检解析方式存在不同口径。
例如代码默认杠杆与模板不同、环境变量可遮蔽部分 dotenv 值、旧普通邮件持仓政策已经过时。
部分风险配置非法时还会退回默认值，使用者可能误以为自定义限制已生效。

本指南提供当前口径，但没有改变 `.env.example` 或运行配置行为。
未来可统一校验、脱敏有效配置摘要与危险参数明确报错。需保留旧配置兼容性，并审查启动影响。

## 10. 验收分层，避免“跑通一次”冒充全部完成

至少分别报告：

1. 执行流程是否通过：实际订单、成交、保护、平仓与状态终结。
2. 暂算是否自洽：本地成本、费用来源、金额与舍入。
3. 权威精确核验是否通过：实际佣金、资金费、返佣、非 USDT 估值、身份及窗口完整性。

没有第三层证据不能宣布精确净盈亏已核验；两位小数截图一致只是有限一致性证据。
无需为了等待最终对账不断新增交易或重启程序。

## 11. 已出现但仍未归因的运行事件

### `.bot_health` 原子替换 WinError 5

隔离实验已证实读句柄可以产生同类 Windows replace 拒绝。
生产历史事件占用方未知，压力失败比例不是生产概率。
现在不继续压测、不加重试、不改读共享、不改 ACL/杀软。
自然再现时针对准确路径与限定时间收集失败 rename、open/close 进程和共享方式；
“某进程读过文件”不足以证明它阻止那一次替换。

### Telegram 偶发读取超时

PTB 22.8 计算 120s configured read + 10s long-poll timeout = 130s，
日志耗时匹配预算；未及时收到响应的网络原因仍未确认。
保持现有被动记录，不新增常驻任务；自动恢复且命令正常时继续观察，
只有持续中断或实际使用受影响才升级排查。不改 timeout、代理或重试。

证据见 [R3 报告](../r3-followup-diagnostics-20261013.md) 与
[隔离实验](../audits/health_replace_winerror5_20261013/REPORT.md)。
